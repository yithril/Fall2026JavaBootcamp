Part 1: Teach the pattern
Q1

What is the Strategy pattern?

Strategy puts each way of doing a job in its own class. Because every one of those classes shares the same interface, you can swap one for another, even while the program is running.

The class that uses the strategy never asks "which one are you?" It just calls the interface method, and polymorphism makes sure the right version runs.

Q2 · Q3

The problem: store discounts

A store checkout needs to apply discounts. There are several kinds, and the store keeps adding more:

  • No discount: pay the full price
  • 10% off: take 10% off the subtotal
  • $5 off: take $5 off (never below $0)
  • Holiday sale: take 25% off

Notice that every discount does the same job (turn a subtotal into a total), but each one follows a different rule to do it.

Q3

Step 1: give each rule its own class

Each way of discounting gets its own class. Each class keeps its rule inside its own applyDiscount method, and no class knows about the others. These classes are called the concrete strategies.

The highlighted line is the only real difference between these classes. Everything around it is the same shape.

Same method, different rule. All four classes have an applyDiscount(BigDecimal subtotal) method, and each one hides its own math inside it. Because they all share that shape, we can describe it once in an interface. Think of the interface as a plug: every discount is built with the same plug, so the checkout can take any of them.

    Q6
    
Where are the OOP pillars?

    
Two of them do most of the work: the shared interface lets every discount fit, and polymorphism makes the right one run.

    

      
Abstraction (the interface)DiscountStrategy says what every discount can do and hides how. Checkout only ever talks to the interface.

      
PolymorphismThe same line, strategy.applyDiscount(subtotal), runs different code depending on which object is plugged in.

      
EncapsulationEach class keeps its own rule. TenPercentOff knows nothing about holiday sales.

      
Implementing an interfaceEvery discount says implements DiscountStrategy. Leave that off and it won't fit, just like the Coupon card.

What makes this harder to work with

    
    
      
  • Java has to check every condition in order until one matches. And the same checks happen again in label().
    • 
      
  • Every new discount means editing this class in two places. Miss one and the program breaks at runtime.
    • 
      
  • Typos compile. total("holday", subtotal) compiles fine and crashes only when the program runs.
    • 
      
  • The class keeps growing. Ten discounts means two if/else chains with ten branches each.
    • 
    

    
"That looks fine to me." With four discounts, it kind of does. The if/else version works. The real cost shows up when the code has to change, and in a real store, it changes all the time. Let's add a discount and see.

    Q9
    
      When is Strategy too much?
      
    
      
      
      Good fit
        
        
          
      • You have several ways to do the same job.
        • 
          
      • New ways get added over time.
        • 
          
      • You need to switch while the program is running.
        • 
        
      
      
      
      
      Probably overkill
        
        
          
      • There is only one way to do the job.
        • 
          
      • There are two options and that will never change.
        • 
          
      • Each option is one short line. A simple if/else is easier to read.
        •
